# TorqueAI External Dispatch Connector Design Gate

Status: design gate only. No live TorqueAI request, database write, scheduler, UI, or production behavior is authorized by this document.

## Goal

Add a narrowly scoped, read-only TorqueAI dispatch connector to Polaris so MOR Logistics dispatch data can be retrieved by the Polaris backend without exposing the TorqueAI token to the browser or allowing Polaris to modify TorqueAI.

The first implementation gate must preserve the existing Polaris connector discipline: explicit tenant scope, backend-only secrets, bounded provider access, deterministic validation, sanitized errors, no hidden retries, and tests that prove no write path exists.

## Certified vendor contract from TorqueAI documentation

TorqueAI documents one external dispatch endpoint:

`GET /api/external/dispatches`

Authentication is a Bearer token generated by a TorqueAI administrator. The token is shown only once and TorqueAI stores only its SHA-256 hash. The token must therefore remain only in the deployment secret store.

Documented query parameters:

- `from`: optional `YYYY-MM-DD`; defaults to today UTC.
- `to`: optional `YYYY-MM-DD`; defaults to `from`.
- `page`: optional, 1-based; defaults to `1`.
- `limit`: optional; defaults to `100`; maximum `500`.
- The requested date range is capped at 31 days. A larger range returns HTTP 400.

Documented response envelope:

- `data`: dispatch records.
- `totalCount`: total matching rows.
- `page`: response page number.
- `itemsPerPage`: page size.
- `dateRange`: response `from` / `to` bounds.

Documented dispatch data includes load/order/status/date fields, dispatcher/customer/driver/carrier names, truck/trailer identifiers, loaded miles, currency, total charge, ordered stops with scheduled/actual timing and addresses, and a billing object with rate, subtotal, total, tax, line items, detention charges, and deductions.

Documented status codes are `200`, `400`, `401`, `403`, `405`, `429`, and `500`.

## Security boundary

### Secrets

The deployment secret is:

`POLARIS_TORQUEAI_API_TOKEN`

Rules:

- Never commit the token.
- Never persist the token to PostgreSQL.
- Never return it from an API response.
- Never log the token or the full Authorization header.
- Never expose it through Vite/frontend environment variables.
- Never ask the browser to call TorqueAI directly.
- Tests must use synthetic tokens only.

The TorqueAI origin must be separately configured as:

`POLARIS_TORQUEAI_BASE_URL`

The implementation must require HTTPS, strip a trailing slash, and append only the certified path `/api/external/dispatches`. It must not accept an arbitrary per-request URL from the browser.

### Tenant binding

The provider token is company-specific. The first gate therefore supports exactly one explicitly configured Polaris organization, using a separate deployment setting such as:

`POLARIS_TORQUEAI_ORGANIZATION_SLUG`

The connector must fail closed if the authenticated Polaris organization does not match the configured organization. No cross-tenant fallback is allowed.

Any Polaris API route exposing TorqueAI data must require authenticated tenant context plus `CONNECTOR_READ`.

## Provider access policy

The initial connector is GET-only.

Allowed provider operation:

`GET {configured_base_url}/api/external/dispatches`

Forbidden in the first gate:

- POST, PUT, PATCH, DELETE, or any non-GET provider method.
- Any TorqueAI endpoint other than `/api/external/dispatches`.
- Dispatch creation, update, assignment, status change, billing change, document change, or token administration.
- Browser-to-TorqueAI calls.
- Background scheduler or cron.
- Automatic polling.
- Automatic retry loops.
- Backfill.
- Database persistence.
- Dashboard/Daily Brief business interpretation.

A `429` response must surface as a sanitized provider-rate-limit error in the first implementation gate. It must not trigger an automatic retry.

## Request bounds

The connector must always send explicit date bounds. It must not depend on TorqueAI's implicit UTC default.

Validation rules:

- `from` and `to` must be ISO dates.
- `from <= to`.
- inclusive date range must be at most 31 days.
- page must be an integer >= 1.
- limit must be an integer from 1 through 500.

For the first controlled production certification, use one explicit completed date, `page=1`, and a conservative `limit` no greater than 100. This certification request is a separate operator-approved step after code review/merge; it is not authorized by this design PR.

## Response validation

The parser must reject malformed provider responses rather than guessing.

Required envelope checks:

- top-level payload is an object.
- `data` is a list.
- `totalCount` is a non-negative integer.
- `page` is a positive integer and matches the requested page.
- `itemsPerPage` is a positive integer and no greater than the requested limit / vendor maximum.
- `dateRange` is an object whose parsed bounds match the explicit request.
- number of rows in `data` must not exceed `itemsPerPage`.
- pagination must be internally possible: already-consumed rows must not exceed `totalCount`.

Provider omission is unknown/missing data, never zero.

The first gate must not assume that `loadNumber` is globally unique until a live schema sample and duplicate behavior are certified. It can be exposed as a provider field but must not yet be used as an unqualified durable primary key.

## Data minimization and sanitization

TorqueAI dispatch responses contain operationally sensitive information, including customer names, driver names, vehicle identifiers, stop addresses, coordinates, and billing amounts.

The connector transport/parser may represent documented fields in backend memory, but any Polaris API response introduced in a later gate must be purpose-specific and minimize fields to what the UI/workflow actually needs.

Errors returned to clients must not contain:

- token values.
- Authorization headers.
- full provider response bodies.
- provider stack traces.
- raw HTTP client exceptions containing secrets.

Logs may include sanitized status code, bounded request dates, page, limit, and a stable error code. They must not include the token.

## Pagination design

TorqueAI instructs clients to page using `totalCount`.

The first connector implementation should expose a single-page primitive only. A separate reviewed pagination/orchestration gate may later add bounded multi-page retrieval.

Future pagination, if approved, must:

- use `totalCount` from each validated response.
- cap `limit` at 500.
- increment pages monotonically.
- stop when `page * itemsPerPage >= totalCount`.
- have an explicit maximum pages/rows bound selected for the product use case.
- make no retries unless a later design gate explicitly certifies them.

This separation prevents an apparently simple read from creating an unbounded provider-call loop.

## Proposed first implementation gate

Files should be limited to the smallest backend connector/parser/test surface, expected along these lines:

- `backend/app/connectors/torqueai.py`
- focused unit tests for TorqueAI transport and response validation.

The implementation gate should provide a backend-only function that accepts already-validated organization scope, explicit dates/page/limit, issues exactly one GET, and returns a typed/sanitized parsed page.

It should not add persistence, scheduler logic, dashboard wiring, Daily Brief behavior, or business KPIs.

Tests must prove at minimum:

1. Authorization uses a Bearer header sourced from the deployment environment.
2. Secret values never appear in returned errors/log payloads.
3. Only HTTPS configured origin + exact dispatch path is called.
4. Only GET is used.
5. explicit date/page/limit parameters are sent.
6. 31-day range and 500-row maximum are enforced locally before provider access.
7. 200 response parsing validates the envelope.
8. malformed envelopes fail closed.
9. 400/401/403/405/429/500 become sanitized connector errors.
10. there is no retry on 429 or other provider failure.
11. no database session/write is required by the connector.
12. no frontend code contains or receives the TorqueAI token.

## Controlled live certification gate

After the implementation PR is merged and its exact-head CI is green, perform one operator-approved live request from the backend environment using:

- the configured company TorqueAI origin.
- the stored Render secret.
- one explicit completed date.
- `page=1`.
- `limit<=100`.

Certification should record only sanitized evidence: HTTP status, returned envelope metadata, documented field presence/types, and whether pagination would be required. Do not record the token or a raw payload containing customer/driver/address/billing data.

If the live response differs from the vendor document, stop and update the design/parser before any persistence gate.

## Deferred gates

The following are explicitly deferred:

- durable dispatch tables / migrations.
- provider identity/key strategy.
- historical backfill.
- multi-page orchestration.
- scheduled ingestion.
- incremental synchronization/checkpointing.
- reconciliation/update semantics.
- UI/dashboard dispatch views.
- Daily Brief integration.
- customer/driver financial or performance KPIs.
- combining TorqueAI dispatches with Motive, QuickBooks, fuel, or other providers.
- IP allowlist hardening once a stable outbound network design exists.

Each deferred item requires a separate reviewed gate because it changes provider-call volume, persistence semantics, privacy exposure, or business behavior.

## Acceptance criteria for this design gate

This design gate is complete when:

- only this documentation file changes.
- no TorqueAI request has been made by Polaris as part of the PR.
- no database or Render configuration has been modified by the PR.
- the token remains only in Render's secret environment.
- the next implementation gate is constrained to one GET-page connector/parser with focused tests.
