# Polaris Knowledge Base — End-of-Day Report

**Date:** 2026-08-07

## Executive Summary

Track 4C advanced from authentication foundation into deliberately narrow Motive read-only ingestion. The production authentication decision is now settled on the Company API Key architecture for the current Mor Logistics single-company server-to-server integration. Vehicle ingestion and company-user ingestion were merged, and utilization work remained behind a contract-verification gate rather than being promoted prematurely into production ingestion.

The key engineering theme today was evidence before expansion: provider contracts are certified one endpoint at a time, raw provider diagnostics remain suppressed, tenant isolation and checkpoint durability are preserved, and uncertain provider semantics are represented explicitly as uncertified rather than inferred.

## Official Decisions

1. **Company API Key is the canonical current Motive production authentication model.** PR #119 moved the active production foundation from OAuth to backend-only `MOTIVE_API_KEY` / `X-API-Key` authentication for the current single-company integration. OAuth is deferred for a future multi-tenant/App Marketplace architecture.
2. **`chief-of-staff/` remains the only production runtime.** Hermes TypeScript Motive code remains reference material and is not integrated into the active runtime.
3. **Motive rollout remains incremental and certification-gated.** Vehicle and user ingestion may advance independently after their contracts are verified; utilization must not become ingestion until its provider request contract is understood.
4. **Unknown provider semantics must stay unknown.** `/v1/users` records are persisted as company users; driver classification remains uncertified because no authoritative role/type discriminator has yet been established.
5. **Provider diagnostics must be transformed into Polaris-owned safe semantics.** Raw Motive error text, identifiers, headers, query values, secrets, and metric values are not exposed in APIs, logs, tests, or frontend surfaces.

## Principles Reaffirmed

- Evidence before certification.
- Least-privilege, read-only provider access during rollout.
- Fail closed on malformed or ambiguous provider contracts.
- Never infer provider identity/role semantics without authoritative evidence.
- Tenant-owned persistence and organization isolation are mandatory.
- Checkpoints advance only after successful durable persistence.
- Secret-bearing headers and credentials exist only at the backend HTTP boundary.
- Retries are bounded; `401`/`403` are not retried, while `429` honors `Retry-After` when available.
- Existing QuickBooks and Outlook behavior remains outside Track 4C changes unless explicitly scoped.

## Engineering Decisions

### Persistence

Existing Motive schema was sufficient for Track 4C.2A and 4C.2B; no new migration was required. Vehicle uniqueness remains organization + provider vehicle identity. User identity persistence remains organization-owned and reuses existing Motive identity storage.

### Checkpoint Integrity

Vehicle/user checkpoints advance only after durable persistence. Provider failures, rate limits, and database failures preserve the prior checkpoint and write sanitized sync-history state.

### Utilization Verification Boundary

The utilization verifier is intentionally not a sync endpoint. It performs exactly one provider attempt, persists no utilization data, mutates no checkpoint, and returns schema/diagnostic metadata only after redaction and categorization.

### Frontend Boundary

Frontend controls expose safe manual vehicle/user sync actions and safe status metadata only. Secrets, secret environment-variable names, provider payloads, and uncertified driver counts remain absent from frontend output.

## Research / Provider Contract Notes

Motive support case 11006147 established Company API Key as the recommended authentication mechanism for the current single-company server-to-server integration and confirmed organization-scoped access plus endpoints including `/v1/vehicles`, `/v1/users`, `/v1/vehicle_utilization`, `/v1/driver_utilization`, and `/v1/ifta/summary`.

Confirmed `/v1/users` pagination uses one-based `page_no`, `per_page` up to 100, and `pagination.total`. No authoritative driver role/type discriminator is yet certified from current Polaris evidence.

For vehicle utilization, current repository evidence shows that the request reaches Motive but receives HTTP 400. The observed provider JSON includes `error_message`; Polaris now maps this content only into fixed semantic categories such as missing/invalid date, vehicle, pagination, user context, permission context, invalid request parameters, or unknown provider rejection. This diagnostic classification is evidence-gathering only and does not certify utilization ingestion.
