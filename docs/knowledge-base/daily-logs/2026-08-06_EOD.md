PR #119 has now established the intended Motive Company API Key production foundation on `main`. PR #120 was accidentally merged after that work, but it was test-only, changed only `chief-of-staff/frontend/tests/motive-frontend.test.mjs`, introduced no production runtime behavior, and was fully reverted by PR #122. The test additions from PR #120 are no longer part of current `main`.

## Official decisions and principles

- `chief-of-staff/` remains the only production runtime. Hermes TypeScript Motive code remains reference material and is not integrated into production.
- Motive production authentication for the current Mor Logistics single-company integration is Company API Key.
- OAuth remains deferred future architecture for multi-tenant or App Marketplace-style Motive integrations; it is not the current production authentication path.
- Provider credentials and secrets remain backend-only. The frontend must never accept, display, retrieve, or construct provider credentials.
- Motive production integration remains deliberately narrow: authenticate/verify first; broad synchronization, polling, webhooks, fleet KPIs, and provider-data ingestion remain deferred.
- Connector diagnostics must be operationally useful without leaking OAuth codes, state values, access/refresh tokens, client secrets, API keys, or authorization headers.
- Existing QuickBooks and Outlook behavior is outside the Motive change boundary and must remain unchanged.
- Provider-confirmed contracts take precedence over an earlier assumed authentication design. Architecture may change when better primary evidence is obtained, but the change must remain explicit, reviewable, and migration-safe.

### Track 4C.1E - Company API Key production foundation

PR #119 changed the production authentication foundation from OAuth 2.0 to a **Motive Company API Key** model for the current Mor Logistics single-company server-to-server use case. This is the intended production architecture based on Motive API Support case **11006147**.

The credential precedence is:

1. secure backend environment variable `MOTIVE_API_KEY`;
2. no database API-key fallback in this change.

The live verification boundary is intentionally limited to one read-only request:

`GET https://api.gomotive.com/v1/vehicles?per_page=1&page_no=1`

with `X-API-Key` supplied only at the backend HTTP boundary.

## Engineering decisions

### Production observability and secret handling

PR #118 made Motive OAuth callback diagnostics searchable in deployed logs while preserving redaction. Sensitive Motive callback query parameters are redacted in Uvicorn access logs, and diagnostic rendering exposes only explicitly safe metadata. Repeated logging configuration remains idempotent and Outlook diagnostic behavior is preserved.

### Persistence diagnostics

PR #117 introduced explicit callback-stage diagnostics around OAuth state lookup, token receipt, organization resolution, encryption, credential persistence, commit, status visibility, exceptions, rollback status, and redirect. This established a general principle: connector persistence failures should identify the failing stage without exposing credentials.

### Authentication architecture correction

PR #119 records Motive API Support case **11006147** as confirming Company API Key authentication for the current single-company server-to-server integration. It also records confirmed read endpoints for vehicles, users, vehicle utilization, driver utilization, and IFTA summary, plus pagination and rate-limit guidance. OAuth remains documented only as a deferred future multi-tenant/App Marketplace option.

## Research notes

Provider guidance recorded today indicates:

- Company API Key is recommended for the current Mor Logistics single-company server-to-server integration.
- Confirmed endpoints include `/v1/vehicles`, `/v1/users`, `/v1/vehicle_utilization`, `/v1/driver_utilization`, and `/v1/ifta/summary`.
- Users pagination uses one-based `page_no`, supports `per_page` up to 100, and exposes `pagination.total`.
- `429` responses should respect `Retry-After` when present and otherwise use exponential backoff with jitter; immediate retry loops and excessive concurrency should be avoided.
- Broad provider synchronization and driver-role filtering remain deferred until production fields/contracts are observed or officially documented.
