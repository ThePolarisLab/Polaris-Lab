## Official Decisions

- Keep Track 4C.2C0 as a bounded contract-verification exercise; do not convert it into production ingestion merely because a non-empty response has now been observed.
- Treat `vehicle_idle_rollups` with wrapper `vehicle_idle_rollup` as the production-observed success shape from the controlled experiment, superseding the old synthetic `vehicle_utilization` success fixture as a production assumption.
- Do not treat `driving_time` or `idle_time` as reporting-period fields. They are utilization metrics.
- Treat request-window period identity as requiring design review because the observed non-empty provider item did not expose true reporting-period start/end fields.
- Preserve the existing safety boundary: no utilization persistence, checkpoint mutation, scheduler, KPI activation, broad sync, speculative `X-User-Id`, or restoration of `X-Time-Zone`.

## Principles Reaffirmed

- Evidence before implementation.
- Provider behavior must be observed and recorded before durable mapping is designed.
- A successful HTTP response does not by itself certify business semantics.
- Diagnostics must remain sanitized: provider IDs, VINs, vehicle numbers, metric values, API keys, and other sensitive/provider data are not exposed through verification output.
- Experiments remain bounded, read-only, and reversible until the contract and semantics are sufficiently understood.

## Engineering Decisions

### PR #135 — Bounded multi-vehicle utilization schema verifier

Merged today. The temporary verifier now:

- selects up to three organization-owned stored Motive vehicles, ordered by internal row ID;
- sends repeated `vehicle_ids[]` values in exactly one `GET /v1/vehicle_utilization` request;
- preserves the completed-day date window, `per_page=1`, and `page_no=1`;
- keeps `X-Time-Zone` and `X-User-Id` absent;
- preserves backend-only `X-API-Key` and optional `X-Metric-Units` behavior;
- reports only sanitized selected-vehicle count metadata;
- does not persist utilization or mutate checkpoints.

Reported validation: 41 focused verifier tests, 290 backend tests, 18 database/security gate tests, 74 targeted QuickBooks/Outlook/runtime regressions, 159 root Jest/TypeScript tests, 35 frontend tests, frontend build, and `git diff --check` all passed.

### PR #136 — Record non-empty schema and fix period detection

Merged today. The production-observed non-empty response established:

- top-level container: `vehicle_idle_rollups`;
- item wrapper: `vehicle_idle_rollup`;
- observed item keys: `driving_fuel`, `driving_time`, `idle_fuel`, `idle_time`, `utilization`, and `vehicle`;
- nested vehicle keys: `id`, `make`, `metric_units`, `model`, `number`, `vin`, and `year`;
- vehicle identity path: `vehicle.id`;
- pagination keys: `page_no`, `per_page`, `total`;
- unit metadata path under `vehicle.metric_units`;
- no observed provider utilization-record ID path;
- no true reporting-period start/end fields in the observed item.

The verifier's period detection was tightened so duration metrics such as `driving_time` and `idle_time` cannot be mistaken for period fields. Unsafe container/wrapper keys continue to be filtered from sanitized diagnostics.

Reported validation: 43 focused verifier tests, 292 backend tests, 52 database/security/QuickBooks/Outlook/runtime tests, 159 root Jest/TypeScript tests, 35 frontend tests, frontend build, and `git diff --check` all passed.

## Research Notes

The non-empty production observation materially reduces schema uncertainty but exposes a new semantic boundary: the provider item supplies utilization metrics and vehicle identity without explicit reporting-period fields. Therefore the request window may need to become part of durable period identity, but that is a design decision rather than an inference to encode automatically.

The observed `vehicle.metric_units` field provides unit-related metadata, but its durable interpretation and relationship to metric values must be reviewed before KPI or persistence design is certified.

The absence of a provider utilization-record ID also means durable uniqueness/idempotency cannot simply be based on a provider record identifier. Any future persistence key will require explicit design using verified identity and period semantics.
